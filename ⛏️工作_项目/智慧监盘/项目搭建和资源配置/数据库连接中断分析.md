## 问题背景

线上接口报错：

```
com.mysql.cj.jdbc.exceptions.CommunicationsException: Communications link failure
The last packet successfully received from the server was 11,441 milliseconds ago.
```

涉及的 SQL：

```sql
SELECT COUNT(*) AS total 
FROM t_panel_record tpr 
WHERE del_flag = 0 
  AND alarm_source = 1 
  AND unit_id = 1 
  AND data_source_type = 'FQ'
  AND EXISTS (
    SELECT 1 FROM t_alarm_record tar 
    WHERE tar.id = tpr.alarm_record_id 
      AND tar.status = 2 
      AND tar.end_time IS NOT NULL
  )
```

## 核心结论

**不是数据库阻塞，而是连接丢失。**

报错 `Communications link failure` 表明应用程序与数据库之间的网络连接断开，而不是传统的事务阻塞（Lock Wait Timeout）。

## 可能原因

### 1. 数据库服务端主动断开（最常见）

- **连接超时 (wait_timeout)**：连接池中的连接闲置时间超过 MySQL 的 `wait_timeout`（默认 8 小时），MySQL 主动关闭连接
- **数据库重启/崩溃**：MySQL 服务重启或崩溃导致连接强行切断
- **数据包过大 (max_allowed_packet)**：查询返回的数据包超过限制

### 2. 网络问题

- 防火墙切断长连接
- 网络波动导致 TCP 连接中断

### 3. 查询执行时间过长（Socket Timeout）

SQL 包含 `EXISTS` 子查询和多表关联，如果执行时间超过驱动程序或应用层设置的 `socketTimeout`，客户端会认为连接已死。

## 解决方案

### MySQL 参数调优

#### 1. 延长空闲连接超时时间

```sql
-- 临时修改
SET GLOBAL wait_timeout = 28800;
SET GLOBAL interactive_timeout = 28800;
```

```ini
# 永久修改 (my.cnf 或 my.ini)
[mysqld]
wait_timeout=28800
interactive_timeout=28800
```

#### 2. 增大数据包大小限制

```sql
-- 临时修改
SET GLOBAL max_allowed_packet = 67108864;  -- 64M
```

```ini
# 永久修改
[mysqld]
max_allowed_packet=64M
```

#### 3. 延长网络读写超时

```ini
[mysqld]
net_read_timeout=120
net_write_timeout=120
```

### 应用侧连接池配置（更重要）

根据报错时间（仅 11 秒），问题更可能出在应用端连接池配置：

#### Druid 配置

```yaml
spring:
  datasource:
    druid:
      # 开启连接检测
      test-on-borrow: true
      test-while-idle: true
      validation-query: SELECT 1
      
      # 缩短连接生命周期
      # maxLifetime 必须小于 MySQL 的 wait_timeout
      max-evictable-idle-time-millis: 300000  # 5分钟
```

#### HikariCP 配置

```yaml
spring:
  datasource:
    hikari:
      connection-test-query: SELECT 1
      max-lifetime: 1800000  # 30分钟，必须小于 wait_timeout
```

### SQL 索引优化

针对慢查询优化索引，避免超时：

#### 主表索引（最关键）

```sql
CREATE INDEX idx_tpr_composite 
ON t_panel_record(unit_id, alarm_source, data_source_type, del_flag, alarm_record_id);
```

**设计理由：**
- `unit_id`：区分度最高，放最前面
- `alarm_source` / `data_source_type`：进一步缩小范围
- `del_flag`：避免回表检查
- `alarm_record_id`：构成覆盖索引，直接从索引树获取关联 ID

#### 关联表索引（可选）

```sql
-- 如果 id 已是主键，此步可选
CREATE INDEX idx_tar_check 
ON t_alarm_record(id, status, end_time);
```

### 索引生效验证

```sql
-- 验证索引是否被使用
EXPLAIN SELECT COUNT(*) AS total 
FROM t_panel_record tpr 
WHERE del_flag = 0 
  AND alarm_source = 1 
  AND unit_id = 1 
  AND data_source_type = 'FQ'
  AND EXISTS (
    SELECT 1 FROM t_alarm_record tar 
    WHERE tar.id = tpr.alarm_record_id 
      AND tar.status = 2 
      AND tar.end_time IS NOT NULL
  );
```

查看结果：
- `key` 列应显示 `idx_tpr_composite`
- `type` 列应显示 `ref` 或 `range`（不是 `ALL`）

如果索引未生效，刷新统计信息：

```sql
ANALYZE TABLE t_panel_record;
```

## 注意事项

- 索引创建后即时生效，无需重启 Java 应用
- 如果统计信息过期，MySQL 优化器可能误判不使用索引
- 应用层不需要重启，SQL 解析和索引选择完全在 MySQL 内部完成
