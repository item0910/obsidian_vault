## 对话内容大致纲要

来源对话：<https://gemini.google.com/share/db73f8f332d5>

这段对话讨论的是一个常见的 Java 异常处理问题：

- 在一个方法里要执行多段工作；
- 其中某一段一旦抛异常，整个方法就直接中断；
- 但实际需求是：**即使某一步失败，后面的其他工作仍然要继续执行**。

Gemini 给出的核心思路是：

- 不要把所有逻辑都放在一个会整体中断的执行链里；
- 对“可能失败、但不应该阻断后续流程”的那一段，用 `try-catch` 单独包起来；
- 这样异常被捕获后，方法还能继续向后执行；
- 如果还有必须执行的收尾动作，可以放到 `finally`。

## 重点复盘点

### 1. 问题本质：异常默认会打断当前执行流程

在 Java 方法里，如果某段代码抛出了异常，而这个异常没有在当前层被捕获，那么：

- 当前方法会提前结束；
- 后面的代码不会继续执行；
- 异常会继续往上抛。

例如：

```java
public void doWork() {
    taskA();
    taskB(); // 这里抛异常
    taskC(); // 不会执行
}
```

如果 `taskB()` 抛异常且没有捕获，`taskC()` 就跑不到。

---

### 2. 解决思路：把可能失败的步骤单独 `try-catch`

如果业务上几个步骤是相对独立的，那么可以把“允许失败但不能影响后续”的步骤单独包起来。

例如：

```java
public void doWork() {
    taskA();

    try {
        taskB();
    } catch (Exception e) {
        // 记录异常
        System.err.println("taskB 执行失败：" + e.getMessage());
    }

    taskC();
}
```

这样效果就是：

- `taskA()` 正常执行；
- `taskB()` 就算失败，也会被捕获；
- `taskC()` 仍然继续执行。

这个模式特别适合：

- 发通知失败，但主流程还得继续；
- 写日志失败，但业务不能中断；
- 某个附属动作失败，不应影响主结果。

---

### 3. 如果有多个独立步骤，可以分别保护

如果一个方法里有多个彼此独立的工作单元，建议按“步骤粒度”分别处理，而不是一把大 `try-catch` 全包。

例如：

```java
public void performMultipleTasks() {
    taskA();

    try {
        taskB();
    } catch (Exception e) {
        System.err.println("taskB 执行失败：" + e.getMessage());
    }

    try {
        taskC();
    } catch (Exception e) {
        System.err.println("taskC 执行失败：" + e.getMessage());
    }

    taskD();
}
```

这样更清楚：

- 哪一步允许失败；
- 哪一步失败后继续；
- 哪一步必须成功。

比起把所有东西塞进一个大 `try-catch`，这种写法更容易维护。

---

### 4. `finally` 适合放“无论成功失败都必须执行”的收尾逻辑

如果有下面这些动作：

- 关闭文件流
- 关闭数据库连接
- 释放锁
- 清理线程上下文
- 打印统一结束日志

那么更适合放在 `finally` 中。

例如：

```java
try {
    taskB();
} catch (Exception e) {
    System.err.println("taskB 执行失败：" + e.getMessage());
} finally {
    System.out.println("清理资源...");
}
```

也就是说：

- `catch` 解决的是“出了异常怎么办”；
- `finally` 解决的是“无论出不出异常都要做什么”。

## 引申知识点

### 1. 要先区分“主流程”与“附属流程”

不是所有异常都应该吞掉。

更合理的做法是先区分：

#### 必须成功的主流程

比如：

- 保存核心业务数据
- 扣减库存
- 提交关键事务

这些步骤如果失败，通常就应该中断并抛异常，而不是继续往下跑。

#### 允许失败的附属流程

比如：

- 发消息通知
- 记录扩展日志
- 调用非关键第三方接口
- 做补充统计

这些步骤如果失败，通常可以捕获异常、记录日志，然后继续执行。

所以关键不是“所有异常都不影响后续”，而是：

- **该中断的中断；**
- **可降级的降级。**

---

### 2. 更推荐“记录异常后继续”，而不是静默吞掉

如果只是这样写：

```java
try {
    taskB();
} catch (Exception e) {
}
```

虽然流程继续了，但后续排查会很痛苦。

更合理的写法至少要：

- 打日志；
- 带上业务标识；
- 必要时记录参数上下文。

例如：

```java
try {
    sendNotice(orderId);
} catch (Exception e) {
    log.error("发送通知失败, orderId={}", orderId, e);
}
```

这样后面出了问题还能追。

---

### 3. 一个更贴近业务的例子

例如订单处理流程：

```java
public void handleOrder(Long orderId) {
    // 主流程：必须成功
    saveOrder(orderId);

    // 附属流程：失败不影响主流程完成
    try {
        sendMessage(orderId);
    } catch (Exception e) {
        log.error("发送消息失败, orderId={}", orderId, e);
    }

    try {
        writeOperateLog(orderId);
    } catch (Exception e) {
        log.error("记录操作日志失败, orderId={}", orderId, e);
    }
}
```

这里的设计就比较合理：

- 订单保存失败：应中断；
- 发消息失败：记录后继续；
- 写操作日志失败：记录后继续。

## 可直接记住的结论

- Java 中异常如果不捕获，会直接中断当前方法，后续代码不再执行。
- 如果想“某一步失败但后面继续”，就把该步骤单独放进 `try-catch`。
- `catch` 负责处理异常，`finally` 负责执行必须收尾的动作。
- 不是所有异常都该吞掉，关键是区分：
  - 哪些是主流程，失败必须中断；
  - 哪些是附属流程，失败可以记录后继续。
- 生产代码里，允许继续执行的异常也应该做好日志记录，避免后续无法排查。
