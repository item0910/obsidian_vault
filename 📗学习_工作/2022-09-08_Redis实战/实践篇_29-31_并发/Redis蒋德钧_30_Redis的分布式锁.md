## 学习之前 : 分布式锁和单机锁的联系和区别

- 单机锁: 控制一个本地值, 需要使用则将其改为 1, 释放则改为 0; 如果使用前已经有别的线程将其改为了 1, 那么就阻塞等待.
- 分布式锁: 给多个实例上的锁变量完成加锁操作.

## Redis 的分布式锁

### 1. 基于单个 Redis 节点实现分布式锁

- 原理
	- 加锁
		设置一个 key: lock_key, value :0 的初始锁值, 通过命令来为其设置值, 实现加锁; 其它锁发现已经有值, 则阻塞
	- 释放锁
		将上值改为 0 或者删除, 实现释放.

- 方法

	```sh
	SETNX key value
	```

	SETNX 命令: 如果没有值, 则设置; 如果有值, 则放弃设置.
	组合完成加锁和释放的操作:

	```sh
	// 加锁
	SETNX lock_key 1
	// 业务逻辑
	DO THINGS
	// 释放锁
	DEL lock_key
	```

- 风险与解决
	- 风险 1: 如果加锁之后, 加锁客户端出现了故障无法释放, 那么锁就相当于被这个客户端一直持有
		- 解决: 给锁变量设置一个过期时间.

			```sh
			SET key value [EX seconds | PX milliseconds]  [NX]
			```

	- 风险 2: 如果 A 加锁之后, B 执行了 DEL, 则锁被释放;
		- 解决: 给加锁的实例设置识别.

			```sh
			// 加锁, unique_value作为客户端唯一性的标识
			SET lock_key unique_value NX PX 10000
			```

			解释: unique_value 是客户端的唯一标识，可以用一个随机生成的字符串来表示，PX 10000 则表示 lock_key 会在 10s 后过期
		- 使用 lua 脚本释放锁的伪代码, 因为释放锁的操作包括读取, 判断, 删除 多个操作.

			```
			//释放锁 比较unique_value是否相等，避免误释放
			if redis.call("get",KEYS[1]) == ARGV[1] then
			    return redis.call("del",KEYS[1])
			else
			    return 0
			end
			```

			执行下面的命令完成释放

			```sh
			redis-cli  --eval  unlock.script lock_key , unique_value 
			```

### 2. 基于多个 Redis 节点实现高可靠的分布式锁

为了避免 Redis 因为实例故障而导致锁无法工作的问题, 开发者提出了 RedLock 算法 (已经不推荐), 算法的基本思想就是, 如果获得了分布式系统中半数以上的锁 (共识算法), 则表示加锁成功.
比如, 属于你的节点的共享数据需要修改, 但是你的锁挂了, 你可以去别的地方获取超过半数的锁, 仍然可以完成修改.
1. 第一步是，客户端获取当前时间。
2. 第二步是，客户端按顺序依次向 N 个 Redis 实例执行加锁操作。
	这一步需要给锁设置一个加锁时间, 这个时间是远远小于锁有效时间的. 一般就是几十毫秒
3. 完成所有加锁步骤后, 看是否超过了半数, 并计算总的加锁时间, 时间必须小于锁的有效时间, 如果两个条件都满足, 我们需要重新计算锁的有效时间, 为**原来的有效时间 - 加锁总耗时**, 如果共享操作已经无法在这个时间内完成了, 那么我们可以直接释放 (放弃这次执行), 以免出现还没完成锁就过期了.

## 评论区收获和思考

- 问: 我们是否可以用下面的方式来实现加锁操作呢？

	```sh
	// 加锁
	SETNX lock_key unique_value
	EXPIRE lock_key 10S
	// 业务逻辑
	DO THINGS
	```

	- 答: 不可以, 没有保证操作的原子性, 如果给锁赋值之后系统故障了, 就不能设置过期时间了
