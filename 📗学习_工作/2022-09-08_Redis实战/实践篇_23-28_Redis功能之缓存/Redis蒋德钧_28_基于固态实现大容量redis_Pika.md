## 学习之前

为了保存更多的数据:
- 集群的问题: 管理难度增加
- 大内存的 Redis 的问题: 实例恢复, 主从同步等会有一系列潜在问题

## 基于固态实现大容量 redis_Pika

Pika 的两个目标:
1. 单实例保存大容量数据, 并规避主从同步和实例恢复的问题
2. 可以与 Redis 兼容

### 1. Pika 整体架构

![[附件/image/28_基于固态实现大容量redis_Pika.jpg]]
- 网络框架: 负责底层网络的请求的接受和发送 (pika 已对操作系统的网络函数进行了封装)
- Pika 线程模块: 采用多线程模型来处理请求: 包括一个请求分发线程, 一组工作线程以及一个线程池
	- 工作模式: 请求分发线程监听网络端口, 收到连接请求后, 就与客户端接力连接, 并把连接交给工作线程处理. 工作线程接收到客户端的请求, 把请求封装成 Task , 交给线程池中的线程执行.(实际的存取)
	- 优点: 通过工作线程的数量来控制请求吞吐率.
- Nemo 模块实现 Pika 与 Redis 兼容, 这样当我们把 Redis 迁移到 Pika 时, 不需要额外修改代码. 而且可以沿用 Redis 的经验. 我们需要关心的是 Nemo 对 Redis 具体类型数据的转换.
- RocksDB(与操作系统交互的底层) 提供的基于 SSD 保存数据的功能, 使 Pika 不用大容量内存就能保存更多数据, 还避免了内存快照, 使用 binlog 机制记录写命令, 用于主从节点的命令同步. 避免了大内存实例的一些问题.

### 2. Pika 如何保存更多数据

- RocksDB 的写数据机制: 使用 Memtable 1, 2 两个小内存, 一旦其中一个写满, 则将其写入 SSD, 并切换下一个.
	![[附件/image/28_基于固态实现大容量redis_Pika-1.jpg]]
- RocksDB 读数据机制: 先在 Memtable 中查找, 如果没有找到, 再去 SSD 中查找.
- Pika 可以直接从存储中读取数据恢复, 避免了大内存快照生成效率低的问题
- Pika 利用 binlog 来完成全量同步, pika 在接受到全量同步的命令时, 会在写入 Memtable 的同时, 写入 binlog, 全量同步结束后就会从 binlog 把尚未同步的命令读取过来, 这样就可以和主库数据保持一致.
- 当进行增量同步时，从库也是把自己已经复制的偏移量发给主库，主库把尚未同步的命令发给从库，来保持主从库的数据一致。
- 好处: binlog 比较大, 不受限制, binlog 增大时, 还可以轮替生成新的 binlog 并把旧的独立保存. 避免了缓冲区溢出的问题.

### 3. Pika 如何与 Redis 兼容 (数据结构层面)

RocksDB 只提供了单值的键值对, 所以要对 Redis 的数据进行转化.

- List
List 集合的 key 被嵌入到了单值键值对的键当中，用 key 字段表示；而 List 集合的元素值，则被嵌入到单值键值对的值当中，用 value 字段表示。因为 List 集合中的元素是有序的，所以，Nemo 模块还在单值键值对的 key 后面增加了 sequence 字段，表示当前元素在 List 中的顺序，同时，还在 value 的前面增加了 previous sequence 和 next sequence 这两个字段，分别表示当前元素的前一个元素和后一个元素。
此外，在单值键值对的 key 前面，Nemo 模块还增加了一个值“l”，表示当前数据是 List 类型，以及增加了一个 1 字节的 size 字段，表示 List 集合 key 的大小。在单值键值对的 value 后面，Nemo 模块还增加了 version 和 ttl 字段，分别表示当前数据的版本号和剩余存活时间（用来支持过期 key 功能），如下图所示：
![[附件/image/28_基于固态实现大容量redis_Pika-2.jpg]]
- Set 集合 (不排序)
Set 集合的 key 和元素 member 值，都被嵌入到了 Pika 单值键值对的键当中，分别用 key 和 member 字段表示。同时，和 List 集合类似，单值键值对的 key 前面有值“s”，用来表示数据是 Set 类型，同时还有 size 字段，用来表示 key 的大小。Pika 单值键值对的值只保存了数据的版本信息和剩余存活时间，如下图所示：
![[附件/image/28_基于固态实现大容量redis_Pika-3.jpg]]
- Hash
对于 Hash 类型来说，Hash 集合的 key 被嵌入到单值键值对的键当中，用 key 字段表示，而 Hash 集合元素的 field 也被嵌入到单值键值对的键当中，紧接着 key 字段，用 field 字段表示。Hash 集合元素的 value 则是嵌入到单值键值对的值当中，并且也带有版本信息和剩余存活时间，如下图所示：
![[附件/image/28_基于固态实现大容量redis_Pika-4.jpg]]

- Sorted Set
最后，对于 Sorted Set 类型来说，该类型是需要能够按照集合元素的 score 值排序的，而 RocksDB 只支持按照单值键值对的键来排序。所以，Nemo 模块在转换数据时，就把 Sorted Set 集合 key、元素的 score 和 member 值都嵌入到了单值键值对的键当中，此时，单值键值对中的值只保存了数据的版本信息和剩余存活时间，如下图所示：
![[附件/image/28_基于固态实现大容量redis_Pika-5.jpg]]

### 4. Pika 的其它优势和不足

- 优势:
	1. 实例重启快, 因为在 SSD 上, 不需要恢复
	2. 全量同步不需要担心缓存溢出, 风险低.
- 不足:
	1. 性能, SSD, binlog
	2. 多线程弥补了不足.
![[附件/image/28_基于固态实现大容量redis_Pika-6.jpg]]
 - AOF 迁移指令

```sh
aof_to_pika -i [Redis AOF文件] -h [Pika IP] -p [Pika port] -a [认证信息]
```
