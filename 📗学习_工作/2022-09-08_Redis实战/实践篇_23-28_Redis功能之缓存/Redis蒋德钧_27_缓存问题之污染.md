## 学习之前: 什么是缓存污染 ->淘汰

访问非常少的数据保存在缓存中.

## 缓存问题之污染

### 淘汰策略之 volatile-ttl

根据过期时间淘汰数据
- 明确知道数据访问时间时, 可以按照这个策略来进行淘汰
- 其它情况不能满足

### 淘汰策略之 LRU(Redis)

- Redis 会在数据中保存时间戳, 然后随机取 N 个, 取最旧的淘汰, 然后在这个基础上不断更新.
- 在处理扫描式的访问时, 无法准确处理, 扫描的一批数据都会被标上最新的时间戳.
	- 解决办法 LFU

### 淘汰策略之 LFU

- LFU 是在 LRU 的基础上, 增加了数据的访问计数,
- 方法: 在 RedisObject 的 24 bit 的 lru 字段拆分成 16 个字节的 ldt, 用来记录时间戳, 8 个字节的 counter 值, 用来记录数据的访问次数. 255 是上限吗? 其实不然.

> LFU 策略实现的计数规则是：每当数据被访问一次时，首先，用计数器当前的值乘以配置项 **lfu_log_factor** 再加 1，再取其倒数，得到一个 p 值；然后，把这个 p 值和一个取值范围在（0，1）间的随机数 r 值比大小，只有 p 值大于 r 值时，计数器才加 1。
> 下面这段 Redis 的部分源码，显示了 LFU 策略增加计数器值的计算逻辑。其中，baseval 是计数器当前的值。计数器的初始值默认是 5（由代码中的 LFU_INIT_VAL 常量设置），而不是 0，这样可以避免数据刚被写入缓存，就因为访问次数少而被立即淘汰。

```sh
double r = (double)rand()/RAND_MAX;
...
double p = 1.0/(baseval*server.lfu_log_factor+1);
if (r < p) counter++;   
```

> 使用了这种计算规则后，我们可以通过设置不同的 lfu_log_factor 配置项，来控制计数器值增加的速度，避免 counter 值很快就到 255 了。下表说明了取不同值时的计数递增情况 (**一般设为 10**)

- 衰减机制:

> LFU 策略使用衰减因子配置项 **lfu_decay_time** 来控制访问次数的衰减。LFU 策略会计算当前时间和数据最近一次访问时间的差值，并把这个差值换算成以分钟为单位。然后，LFU 策略再把这个差值除以 lfu_decay_time 值，所得的结果就是数据 counter 要衰减的值。
> 简单举个例子，假设 lfu_decay_time 取值为 1，如果数据在 N 分钟内没有被访问，那么它的访问次数就要减 N。如果 lfu_decay_time 取值更大，那么相应的衰减值会变小，衰减效果也会减弱。所以，如果业务应用中有短时高频访问的数据的话，建议把 lfu_decay_time 值设置为 1，这样一来，LFU 策略在它们不再被访问后，会较快地衰减它们的访问次数，尽早把它们从缓存中淘汰出去，避免缓存污染。

## 评论区收获和思考

- 使用了 LFU 之后, 缓存还会被污染吗?
	- 计数短时间很高, 然后衰减的很慢.
