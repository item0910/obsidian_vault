## 学习之前: 了解概念

雪崩: 大量请求无法在缓存中处理, 积压到数据库层, 使之压力激增
击穿: 热点数据无法访问 (过期失效), 积压到数据库, 使之压力激增
穿透:

## 缓存问题之雪崩,击穿,穿透

### 1. 雪崩的引发和解决

#### 引发和解决

1. 大量数据同时过期, 导致在缓存的大量请求无法处理, 然后导致数据库压力很大
	- 解决: 给数据**设置不同的过期时间**, 加一个 EXPIRE 加一个随机数
	- 部分请求**服务降级**:
		- 非核心数据 比如商品属性等: 暂时停止从缓存查询这些数据, 返回预定义信息, 空值或是错误信息.
		- 核心数据: 比如库存等, 仍然允许查询
2. Redis 宕机, 无法服务, 导致直接访问数据库.
	- 解决: 在业务中设计**服务熔断**, 在 Redis 发生故障时, 不把请求发送到 Redis, 直接返回. 避免连锁效应
	- **请求限流**, 在请求入口设置请求数的最大值, 避免并发压力过大.
3. 预防: 高可靠集群, 主从切换, 设置合理的内存等.

### 2. 击穿的引发和解决

击穿就是针对某个访问频繁的热点数据无法处理 (热点数据失效).
- 解决: 对热点数据不设置过期时间, 并在淘汰机制中将其回避.

### 3. 穿透

访问缓存中没有而且数据库中也没有的数据, 大量请求形成攻击
- 引发
1. 业务层误操作: 缓存和数据库中的数据被删除了, 导致都没有
2. 恶意攻击

- 解决
1. 缓存空值或缺省值. 针对查询的数据, 缓存一个空值或者和业务层协商确定 (在业务层就阻拦了请求) 的缺省值. 避免了大量请求被提交到数据库.
2. 使用布隆过滤器快速判断数据是否存在
	1. 布隆过滤器由一个初始值都为 0 的 bit 数组和 N 个哈希函数组成
	2. 标记某个数据时, 让这个数据分别计算 N 个哈希数值, 然后对长度取模, 得到对应位置, 标 1
	3. 如果数据不存在, 那么对应的位置应该就是 0; 布隆过滤器可以由 Redis 实现
3. 在前端进行检测请求, 判断请求合法性.

## 评论区收获和思考

- 问题: 能用服务熔断, 服务降级, 请求限流来应对缓存穿透问题吗.
	- 不太可, 处理的问题性质不同. 还是要提前判断数据是否存在, 也就是事前拦截, 比如在前端拦截或者布隆过滤器
	- 布隆过滤器: 如果把存在的数据都标 1
		- 存在判不存在: 不会出现
		- 不存在判存在: 有可能
- 布隆过滤器

关于布隆过滤器的使用，还有几点和大家分享。

1、布隆过滤器会有误判：由于采用固定 bit 的数组，使用多个哈希函数映射到多个 bit 上，有可能会导致两个不同的值都映射到相同的一组 bit 上。虽然有误判，但对于业务没有影响，无非就是还存在一些穿透而已，但整体上已经过滤了大多数无效穿透请求。

2、布隆过滤器误判率和空间使用的计算：误判本质是因为哈希冲突，降低误判的方法是增加哈希函数 + 扩大整个 bit 数组的长度，但增加哈希函数意味着影响性能，扩大数组长度意味着空间占用变大，所以使用布隆过滤器，需要在误判率和性能、空间作一个平衡，具体的误判率是有一个计算公式可以推导出来的（比较复杂）。但我们在使用开源的布隆过滤器时比较简单，通常会提供 2 个参数：预估存入的数据量大小、要求的误判率，输入这些参数后，布隆过滤器会有自动计算出最佳的哈希函数数量和数组占用的空间大小，直接使用即可。

3、布隆过滤器可以放在缓存和数据库的最前面：把 Redis 当作布隆过滤器时（4.0 提供了布隆过滤器模块，4.0 以下需要引入第三方库），当用户产生业务数据写入缓存和数据库后，同时也写入布隆过滤器，之后当用户访问自己的业务数据时，先检查布隆过滤器，如果过滤器不存在，就不需要查询缓存和数据库了，可以同时降低缓存和数据库的压力。

4、Redis 实现的布隆过滤器 bigkey 问题：Redis 布隆过滤器是使用 String 类型实现的，存储的方式是一个 bigkey，建议使用时单独部署一个实例，专门存放布隆过滤器的数据，不要和业务数据混用，否则在集群环境下，数据迁移时会导致 Redis 阻塞问题。
