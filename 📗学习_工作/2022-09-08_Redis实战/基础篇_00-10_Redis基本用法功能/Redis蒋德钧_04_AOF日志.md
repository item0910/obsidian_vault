## 学习之前: Redis 的持久化策略

AOF 与 RDB 是 Redis 持久化的两个主要策略

## AOF

AOF: append only file

### 1. AOF 的优点和缺点

1. 传统的先记录后执行的缺点:
	- 如果执行时发生错误, 则日志中的错误也被记录
	- 线程在写日志时对操作有阻塞
2. AOF 的两个风险:
	1. 如果完成了一个操作, 还没有记录日志就宕机了, 那么就有丢失数据的风险
	2. 虽然对当前操作没有阻塞, 但对下一个操作还是有阻塞的

### 2. AOF 是如何执行的

1. 三种策略和优缺点:
	1. Always: 基本做到数据不丢失, 但性能损失很大
	2. No: 操作系统控制写回, 期间数据全部丢失
	3. Everysec: 折中
2. 日志文件太大的烦恼: 1. 文件系统对文件大小有限制 2. 文件过大再追加效率很低 3. 如果发生宕机, 记录要一个一个重新执行, 影响效率 ➡️ AOF 重写 (把重复的操作折叠)
	- 一个拷贝, 两处日志
		1. 一个拷贝: 每次重写 fork 出一个子线程 bgrewriteaof , 主线程会把内存拷贝一份给它, 让他完成重写
		2. 两处日志: 主线程使用的 AOF 日志仍然在正常使用, 另外新的操作也会写入新的 AOF 文件
![[附件/image/04_AOF日志.jpg]]
3. 流程总结:
	1. 每次重写时, 主线程会执行一个内存拷贝, 然后使用两个日志保证过程中的数据不会丢失; 这个过程是采用额外的线程来执行的, 所以不会造成阻塞

### 问题 1. AOF 重写有没有阻塞风险呢?

1. fork 进程时, 有阻塞风险 (内核要把主线程的 PCB 拷贝给子进程, 这与实例的内存大小有关)
2. 写时复制的写时, 主线程会申请新的内存空间, 会产生阻塞风险: 比如遭遇主线程操作 bigkey, 或者操作系统开启了内存大页机制 (复制内存的原理会导致阻塞, 因为操作系统在分配内存空间时有查找和加锁的开销.)

### 问题 2. AOF 重写也有一个重写日志, 为什么不使用本身的日志呢?

1. 共享资源竞争问题, 会造成性能损耗
2. 如果重写失败, 则会造成原本的 AOF 文件被污染, 不能做恢复使用. 得不偿失
