数据结构的复杂度

| 名称     | 时间复杂度 |
| -------- | ---------- |
| 哈希表   | O(1)       |
| 跳表     | O(logN)    |
| 双向链表 | O(N)       |
| 压缩列表 | O(N)       |

### 1. 哈希表

1. Redis 使用了一个哈希表来保存键值对
![[附件/image/02_Redis中的数据类型和其数据结构-1.jpg | 500]]
java 的 HashMap 也是采用的这种结构
![[附件/image/02_Redis中的数据类型和其数据结构-2.jpg | 500]]
2. 渐进式的 Rehash
	1. 给 2 号哈希分配更大的空间
	2. 把哈希表 1 分次拷贝到 2 中
	3. 定时任务会周期性搬迁, 意味着即使没有写操作, 也会以一定频率执行任务.
	4. 表 1 不再添加, 当收到查找任务时, 如果在 1 内没有找到, 则会去 2 找

### 2. 集合类型数据的操作

分五种: 数组, 双向链表, 哈希表, 压缩列表和跳表, 着重介绍一下压缩列表和跳表

- 压缩列表

![[附件/image/02_Redis中的数据类型和其数据结构-4.jpg|500]]

压缩列表表头存储着列表长度, 列表尾的偏移量, 列表 entry 个数; 表尾还有一个 zlend 表示列表结束
这使得我们查找头尾和操作头尾元素的复杂度变为 O(1)

- 跳表

![[附件/image/02_Redis中的数据类型和其数据结构-5.jpg|500]]

增加了基础索引, 实现快速定位, 使查找复杂度降到 O(logN)

### 3. 不同操作的复杂度

- 单元素操作: O(1) * 操作的个数 (针对集合来说)
- 范围操作: O(N), 2.8 开始引进了 SCAN 操作, 是采用渐进式的, 减少了阻塞
- 统计操作: 元素的记录: O(1)
- 特殊操作: 收尾添加元素, List 的 Push 和 Pop 可以直接定位 O(1)

### 问题 1：整数数组和压缩列表作为底层数据结构的优势是什么？

因为元素是挨个连续放置的，我们不用再通过额外的指针把元素串接起来，这就避免了额外指针带来的空间开销。

采用不同的数据结构其实是在内存使用效率和性能之间做出平衡.

## 思考

1. Java 的 hashMap 也是采用了这样的键值对设计
2. 压缩列表的数据结构在协议的设计中也十分常见
3. 数组和压缩列表在查找的时间复杂度上没有优势, 为什么还会把他作为底层的数据结构呢?
	- 内存利用率: 二者内存使用十分紧凑, 因为 Redis 是十分节约内存的.
	- 数组对 CPU 的高速缓存支持更友好, 所以在元素较少时, 从速度上考虑可以采用数组; 元素增多时, 则使用哈希和跳表更合适.
