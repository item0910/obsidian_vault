## 学习之前: 当 Redis 性能不足时

切片集群的两个方向
- 纵向: 优化设备, 比如加大内存, 增加 CPU 个数等, 将实例内存增大
- 横向: 增加同水平级的实例数量: 比如将一个 25G 的实例分为 5 个 5G 的实例, 这样在各项操作时 (fork, 快照, 主从替换等等) 都会性能得到优化.

## Redis_Cluster 切片集群方案

3.0 开始, Redis 提供了一个 Redis CLuster 方案.

### 1. 如何管理切片集群

1. 数据与实例对应:
	1. 使用 cluister create 命令创建集群: Redis 会将这些槽位 (16384) 个平均分配到实例个数上, 当然也可以用 cluster meet 命令手动建立实例间的链接再使用 cluster addslots 指定每个实例上哈希槽的个数.(这样有利于根据每个实例所在的物理机情况分配负载), 手动分配时, 必须把 0 - 16383 个槽位全部分配完.
	2. 每个键值根据自己通过 CRC16 % 16384 之后的模值确定自己的槽位和实例
	3. Redis 每个实例会把自己的哈希槽信息发送给与它相连接的其它实例, 并把它们缓存到客户端, 客户端完成确定应该往哪个实例发送信息.
2. 哈希槽位发生变化时
	1. 情况有:
		- 实例有新增或删除, 哈希槽位需要重新分配
		- 为了负载均衡, 重新分配槽位.
	2. 重定向机制
		- 当客户端再一次通过本地数据访问原槽位时, 该槽位会通过 MOVED 指令通知客户端槽位已经发生变化, 于是客户端再得知这个消息之后, 去新实例访问获取数据, 并更新本地的信息.
	3. 当实例数据迁移一半时, 用户访问了原实例的数据, 那么原实例会返回一个 ASK 报错信息, 指示新的实例地址, 但这里并没有在客户端完成新地址的更新.

```sh	
GET hello:key
(error) MOVED 13320 172.16.19.5:6379
```

```sh
GET hello:key
(error) ASK 13320 172.16.19.5:6379
```

### 问题 1. 为什么要用 CRC 计算进行映射, 不能将对应状况直接存在客户端吗

1. 如果将映射存在本地, 直接的一个结果就可能映射文件很大, 那么随之引发的问题就是: 保存映射文件本身就需要很大的内存, 更新维护这个文件也需要很大的消耗
2. 映射有利于实现负载均衡.

## 思考

左程云关于数据库负载均衡的一次介绍:

1. 先思考把三个实例平均分配的情况, 如下图
![[附件/Excalidraw/Drawing 2022-08-26 21.07.41Redis_redis集群方案.excalidraw]]

2. 这样, 当查询一个键时, 计算他的 key 的 哈希, 去离他最近的那个哈希值的实例查询数据. 这样的好处是: 易判断, 增加实例时只要迁移部分数据
    但这样也会产生一个问题, 就是实例很可能不能负载均衡
3. 于是, 采用下面一种方式, 每个实例通过 1000 个字符串组成的集合形成的哈希均衡分布在这个环上, 比如 m1{1, 2, ... , 1000}, m2{1001, 1002, ... , 2000}...
    这样就能使新增的实例均匀的分布到这个环上了.
