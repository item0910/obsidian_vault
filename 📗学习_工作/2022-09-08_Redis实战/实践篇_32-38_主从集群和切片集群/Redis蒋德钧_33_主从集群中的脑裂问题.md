## 主从集群中的脑裂问题

数据丢失了, 开始排查

### 1. 导致脑裂的原因排查和数据丢失的原因

1. 主库的部分数据尚未同步到从库, 从库升级, 这部分数据丢失
	- 这类原因可以通过复制进度的差值来判断. INFO replication 如果 slave < master, 那么可以判断是数据未同步发生的.
	- 但是这个事例中发现两个是一样的, 说明从库升级前二者数据一致
2. 排查客户端的操作日志, 发现客户端仍在和原主库通信 -> 脑裂: 但这种情况会给不同的主库发送请求, 并不会数据丢失.
3. 原因: 原主库因为某种阻塞被哨兵判断为下线, 主从切换过程中主库还恢复响应了一段时间, 这段时间就会发生数据丢失 (因为后面会删库 RDB 恢复)

### 2. 如何应对脑裂问题

Redis 已经提供了两个配置项来限制主库的请求处理，分别是 min-slaves-to-write 和 min-slaves-max-lag
- min-slaves-to-write：这个配置项设置了主库能进行数据同步的最少从库数量；
- min-slaves-max-lag：这个配置项设置了主从库间进行数据复制时，从库给主库发送 ACK 消息的最大延迟（以秒为单位）。
搭配二者使用, 比如 min-slaves-to-write 设为 1, min-slaves-max-lag 设为 12, 如果哨兵判断下线时间为 10, 那么主库因为某些原因卡了 15s , 原主库也不能接收新的请求了.

## 评论区收获和思考

- 假设我们将 min-slaves-to-write 设置为 1，min-slaves-max-lag 设置为 15s，哨兵的 down-after-milliseconds 设置为 10s，哨兵主从切换需要 5s。主库因为某些原因卡住了 12s，此时，还会发生脑裂吗？主从切换完成后，数据会丢失吗？
	- 答: 会发生 3s. 12s 并没有达到不能接收指令的 15 秒设定值, 而 15(10 + 5) 后原主库将下降为从库, 这个时间差内的数据就会丢失.
- min-slaves-to-write，有一点也需要注意：如果只有 1 个从库，当把 min-slaves-to-write 设置为 1 时，在运维时需要小心一些，当日常对从库做维护时，例如更换从库的实例，需要先添加新的从库，再移除旧的从库才可以，或者使用 config set 修改 min-slaves-to-write 为 0 再做操作，否则会导致主库拒绝写，影响到业务。
