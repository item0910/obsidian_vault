## 学习之前: 主从同步的坑

1. 主从数据不一致
2. 读到过期数据
3. 配置项不合理导致服务挂掉

## Redis 主从同步与故障切换

### 1. 主从数据不一致

- 原因
	1. 主从的命令复制是异步进行的, 所以网络延迟会造成数据不一致
	2. 从库被阻塞 (正在处理复杂度)
- 解决方案
	1. 尽量把主从布置在同一个机房, 减少延迟
	2. 开发一个外部程序来监控主从同步的复制进度.
		- INFO replication 可以查看主从的写命令进度信息, 我们可以由此计算两个进度的偏移量,
		- 如果偏移量差值超过预先设定的阈值, 则可以使客户端不再和这个从库进行通信读取, 可以减少数据不一致的情况, 程序逻辑如下

### 2. 读到过期数据

- 原因
	1. Redis 的删除策略引发.
		- 惰性删除: 到期不会立即删除, 而是等再有请求来读写这个数据时再检查, 如果过期了, 再删除. 这样做的好处是可以减少删除对 CPU 的使用.
		- 定期删除: 每隔一段时间把过期的数据删除.
		- 所以, 如果过期数据很多, 并且一直没有再访问的话, 那么就会留存很多过期数据在 Redis 中, 从库的过期数据就会被读取 (并没有删除)
		- 解决: 但是, 如果使用的是 3.2 以上的版本, 从库也会判断是否过期, 如果过期了, 从库虽然不会删除, 但会返回空值.
	2. 设置过期时间的时差引发. 因为设置的是时间长度, 所以因为网络传输等原因, 过期时间不同.
		![[附件/image/32_Redis主从不一致与故障切换-1.jpg]]
		- 解决: 在业务应用中使用 EXPIREAT/PEXPIREAT 命令，把数据的过期时间设置为具体的时间点，避免读到过期数据。

### 3. 配置项不合理

protected-mode 和 cluster-node-timeout。
1. protected-mode: 哨兵实例能否被其他服务器访问. 这个为 YES 时, 哨兵实例只能在本地访问; no 的时候才能在其他服务器访问这个哨兵.
	- 只能本地访问导致哨兵之间不能通信, 更不能判断主库故障和投票下线, 无法进行主从切换. 合理配置如下:

		```sh
		protected-mode no
		bind 192.168.10.3 192.168.10.4 192.168.10.5
		```

2. cluster-node-timeout: 配置 Redis Cluster 集群的判断异常时间. (主从切换时响应心跳的时间会比较长, 如果超过了这个值就会被判断为异常主库),
	- Redis Cluster 必须要半数以上的实例能正常运行才能正常运行,.
	- 建议调大这个值, 10 - 20 s

### 总结

![[附件/image/32_Redis主从不一致与故障切换-2.jpg]]
- Redis 中的 slave-serve-stale-data 配置项设置了从库在主从复制时, 能否处理数据读写命令，
	- 你可以把它设置为 no。这样一来，从库 (在复制时或者) 与主库断开时, 只能服务 INFO、SLAVEOF 命令，这就可以避免在从库中读到不一致的数据了。

## 评论区收获和思考

- 让从库也可以删除过期数据可以吗 (把 slave-read-only 设置为 no)?
	- 不要, 会导致主从数据不一致.

- 即使从库可以删除过期数据, 也会有数据不一致的风险
	1. 主库在数据快要过期时对数据进行了延时, 而因为网络情况从库没能及时完成延时, 导致了删除, 从而引发主从不一致
	2. 主从库的时钟不同步, 导致主从删除时间不一致.
