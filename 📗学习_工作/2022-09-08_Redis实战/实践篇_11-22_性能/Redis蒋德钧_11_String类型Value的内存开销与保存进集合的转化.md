## 学习之前: 万金油的 String 为什么不好用了

一亿张图片占用了 6.4GB 的内存, 平均一个数据用了 64 字节的数据

## String 类型的内存开销和转换方案

```
photo_id: 1101000051
photo_obj_id: 3301000051
```

### 1. 为什么 String 类型的数据内存开销大

String 保存 64 位有符号整数时, 会把他保存为一个 8 字节的 Long 类型整数, 这种保存方式通常也叫做 int 编码方式. 按照 Long 类型占用 8 个字节来计算, 一个 Long 类型应该可以存下 2 的 64 次方的数字, 完全可以胜任 10 位数, 但为什么一个键值对需要 64 字节呢.

#### (1) String 类型元空间

1. String 类型还需要额外的内存空间记录数据长度, 空间使用等信息, 这被称作元数据, 当需要保存的数据小, 元数据反而会大于需要保存的信息.
	String 用简单动态字符串结构体来保存
	![[附件/image/11_String类型Value的内存开销与保存进集合的转化.jpg]]
	- buf 保存实际数据, 最后加一个 `\0`, 表示结束, 占用 1 个字节
	- len 占四个字节, 表示 buf 的已用长度
	- alloc 占四个字节, 表示 buf 的实际分配长度

#### (2) RedisObject 结构体的开销

![[附件/image/11_String类型Value的内存开销与保存进集合的转化-1.jpg]]

	包含元数据和一个指针, 指针指向具体的数据类型的实际数据

	RedisObject 还对 Long 类型整数和 SDS(动态字符串) 有特别的设计: 当保存的是 Long 类型的整数时, 指针部分就直接赋值为整数数据了, 这样就节省了额外的指针开销; 

	当保存的是字符串数据, 如果字符串小于等于44字节, 那么元数据, 指针和 SDS 是一块连续的区域(可以避免内存碎片), 这也被称为 embstr 编码方式. 当大于44字节时, 这三块区域就不会连续, 会给SDS分配独立的空间, 这种编码方式称为 raw 的编码方式.

	![[11_String类型Value的内存开销与保存进集合的转化-2.jpg]]

先做一个计算总结:

	一个RedisObject占用16字节, Long 类型数据直接存在 ptr 内, 不做计算, 每个ID会占用 8 + 8 = 16 字节, 一个键值对就是32字节, 那么还有 32 字节哪里去了呢?

#### (3) Redis 全局结构体

1. Redis 会使用一个全局哈希表保存所有键值对, 哈希表的每一项是一个 dictEntry 结构体, 用来指向一个键值对.
		![[附件/image/11_String类型Value的内存开销与保存进集合的转化-3.jpg]]
	这三个指针只有 24 字节, 为什么会占用了 32 字节呢, 因为 Redis 的内存分配库 jemalloc 在分配内存时, 会找一个比 N 大, 但是最接近 N 的 2 的幂作为分配的空间, 例如现在要申请 24B 的空间, 就会给你分配 32 字节的空间.

到这里, 正式解释了为什么一个 String 键值对会占用 64 字节.

### 2. 用什么数据结构可以节省内存?

1. 压缩列表
	![[附件/image/11_String类型Value的内存开销与保存进集合的转化-4.jpg]]
	- prev_len，表示前一个 entry 的长度。prev_len 有两种取值情况：1 字节或 5 字节。取值 1 字节时，表示上一个 entry 的长度小于 254 字节。虽然 1 字节的值能表示的数值范围是 0 到 255，但是压缩列表中 zlend 的取值默认是 255，因此，就默认用 255 表示整个压缩列表的结束，其他表示长度的地方就不能再用 255 这个值了。所以，当上一个 entry 长度小于 254 字节时，prev_len 取值为 1 字节，否则，就取值为 5 字节。
	- len：表示自身长度，4 字节；
	- encoding：表示编码方式，1 字节；
	- content：保存实际数据。
	拿一个图像的 ID 为例, pre_len 1 字节 (因为没有超过 254 字节), + len 4 字节 + encoding 1 字节 + content 8 字节, 所以一个图像 id = 1 +4 + 1 + 8 = 14 实际分配 16 字节
2. Redis 基于压缩列表实现了 List, Hash, Sorted Set 这样的集合类型, 这样做的最大好处就是节省了 dictEntry 的开销.
3. 如何存
	1. 图片 ID 的前 7 位作为 hash 类型的键, 图片 ID 的最后 3 位分离, 作为 值 的 key, 图片存储对象 ID 作为 value

	```sh
	127.0.0.1:6379> info memory
	# Memory
	used_memory:1039120
	127.0.0.1:6379> hset 1101000 060 3302000080
	(integer) 1
	127.0.0.1:6379> info memory
	# Memory
	used_memory:1039136

	//可以看到, 这种方式新增一个数据只占用了16个字节
	```

	2. 二级编码的长度也是有讲究的
		- hash-max-ziplist-entries：表示用压缩列表保存时哈希集合中的最大元素个数。
		- hash-max-ziplist-value：表示用压缩列表保存时哈希集合中单个元素的最大长度。

		如果我们往 Hash 集合中写入的元素个数超过了 hash-max-ziplist-entries，或者写入的单个元素大小超过了 hash-max-ziplist-value，Redis 就会自动把 Hash 类型的实现结构由压缩列表转为哈希表。而且不会再转回.

		所以为了我们每个 Hash 集合中的个数不超过 1000 个, 我们将第一个参数设置为 1000, 然后选取三位作为 hash 集合的 Key, 这样就不会超过而导致数据结构发生变化了

## 评论区收获和思考

- 除了 String 和 Hash 还有什么类型适合保存图片 ID
	- Sorted Set

	```sh
	zadd 1101000 3302000080 060
	zscore 1101000 060
	```

	- 问题:
		- Sorted Set 底层是压缩列表时, 插入的性能比不上 Hash
		- 虽然节省了空间, 但是很难设置过期时间. String 则可以解决这个问题.
		- 每次查询都会遍历 list, 性能会下降
	- 实测
		- 长度 7 位数，共 100 万条数据。使用 string 占用 70mb，使用 hash ziplist 只占用 9mb.
