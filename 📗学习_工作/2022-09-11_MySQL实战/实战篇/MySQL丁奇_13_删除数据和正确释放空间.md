## 前言

删了一半数据表大小却没有改变?

本篇讨论的场景, 就是删除了部分数据, 表空间却没有回收.

## 删除数据和正确释放空间

### 参数 innodb_file_per_table

这个参数 on 表示每个表单独有一个文件, 否则放在共享表空间, 为了方便管理, 建议为 on

因为如果是 off, 即使表删掉了, 共享空间内也不会回收.

### 删除数据流程

![[附件/image/13_删除数据和正确释放空间.jpg]]

如果要删除 R4, InnoDB 只会把他标记为已删除, 如果之后要在 300-600 之间再插入一个记录, 可能会复用这个位置, 也就是说, 磁盘文件大小是不会改变的.

假如我们删掉了一整个数据页呢? 那么整个数据页都可以被复用.但和记录复用有所不同, 比如插入一个 800 的数据, 记录不能被复用, 但被标记为可复用的数据页是可以使用的.

所以,**delete **命令只是把表所在的位置或者数据页标记为可复用. 空间是不会被回收的. 这些可复用的位置, 看起来像是 " 空洞 "

如果一个数据页满了, 再想在内部插入一个数据, 就会造成页分裂, 页分裂的结果, 则是分裂出来的两个数据页的利用率都不高.(留下空洞)

我们要解决空洞的问题, 就要重建表

### 重建表

`alter table A engine=InnoDB` 命令来重建表。

![[附件/image/13_删除数据和正确释放空间-1.jpg]]

这个过程中, 花时间的是给临时表插入数据. 5.6 之前, A 不能做更新操作, 后面引入了 online DDL
![数据库操作](MySQL丁奇_00_MySQL术语.md#数据库操作)
引入后, 这个重建流程是:

1. 建立一个临时文件，扫描表 A 主键的所有数据页；
2. 用数据页中表 A 的记录生成 B+ 树，存储到临时文件中；
3. 生成临时文件的过程中，将所有对 A 的操作记录在一个日志文件（row log）中，对应的是图中 state2 的状态；
4. 临时文件生成后，将日志文件中的操作应用到临时文件，得到一个逻辑数据上与表 A 相同的数据文件，对应的就是图中 state3 的状态；
5. 用临时文件替换表 A 的数据文件。

![[附件/image/13_删除数据和正确释放空间-2.jpg]]
alter 语句在启动的时候需要获取 MDL 写锁，但是这个写锁在真正拷贝数据之前就退化成读锁了。为什么要退化呢？为了实现 Online，MDL 读锁不会阻塞增删改操作。

获取这个锁的目的就是为了不让其它线程来同时 DDL, 这个过程非常短, 所以可以认为是 online 的

上述的这些重建方法都会扫描原表数据和构建临时文件。对于很大的表来说，这个操作是很消耗 IO 和 CPU 资源的。因此，如果是线上服务，你要很小心地控制操作时间。如果想要比较安全的操作的话，我推荐你使用 GitHub 开源的 **gh-ost** 来做。

### Online 和 inplace

inplace 是一种行为逻辑

复制表有两个逻辑 一个 copy , 一个 inplace

```sql
alter table t engine=innodb,ALGORITHM=inplace;
alter table t engine=innodb,ALGORITHM=copy;
```

比如新建索引:

```sql
alter table t add FULLTEXT(field_name);
```

这个过程就是 inplace 的, 但是这个操作不是 online 的, 会阻塞增删改操作.

另外:

analyze table t 不是重建表，只是对表的索引信息做重新统计，没有修改数据，这个过程中加了 MDL 读锁；

optimize table t 等于 recreate+analyze。

### 小结

1. 从 delete 数据不会释放空间开始说起, 谈到了如何正确的删除表
2. 为了释放空间, 我们需要重新组织表的存储, 可以用 alter table A engine=InnoDB
3. inplace 的行为在整理表是不阻塞读写的, 但是在新建索引时, 是阻塞读写的.

## 删除数据和正确释放空间思考

- 假设现在有人碰到了一个“想要收缩表空间，结果适得其反”的情况，看上去是这样的：
    - 一个表 t 文件大小为 1TB；
    - 对这个表执行 alter table t engine=InnoDB；发现执行完成后，空间不仅没变小，还稍微大了一点儿，比如变成了 1.01TB。你觉得可能是什么原因呢 ？
        - 答: 执行过程中可能又有新的数据插入造成表分裂.
