## MySQL' 饮鸩止渴 ' 提高性能的方法

### 短连接风暴

- 引发原因
正常的短连接模式就是连接到数据库后，执行很少的 SQL 语句就断开，下次需要的时候再重连。但是连接的成本很高 (通常采用数据库连接池的方式).

短连接模型存在一个风险，就是一旦数据库处理得慢一些，连接数就会暴涨。max_connections 参数，用来控制一个 MySQL 实例同时存在的连接数的上限，超过这个值，系统就会拒绝接下来的连接请求，并报错提示“Too many connections”。对于被拒绝连接的请求来说，从业务角度看就是数据库不可用。

- 解决办法
1. 处理掉站着链接不用的线程, 优先断开不在事务中的查询.

	show processlist 发现
	![[附件/image/22_MySQL'饮鸩止渴'提高性能的方法-1663598774026.jpeg]]
	两个会话都是 sleep
	查 information_schema 库的 innodb_trx 表。
	![[附件/image/22_MySQL'饮鸩止渴'提高性能的方法-1663598827926.jpeg]]
	从服务端断开连接使用的是 kill connection + id 的命令， 一个客户端处于 sleep 状态时，它的连接被服务端主动断开后，这个客户端并不会马上知道。直到客户端在发起下一个请求的时候，才会收到这样的报错“ERROR 2013 (HY000): Lost connection to MySQL server during query”。

	从数据库端主动断开连接可能是有损的，尤其是有的应用端收到这个错误后，不重新连接，而是直接用这个已经不能用的句柄重试查询。这会导致从应用端看上去，“MySQL 一直没恢复”。

	即使只是一个断开连接的操作，也要确保通知到业务开发团队。

2. 减少连接过程中的损耗. 一种可能的方法: 跳过权限验证
	跳过权限验证的方法是：重启数据库，并使用–skip-grant-tables 参数启动。这样，整个 MySQL 会跳过所有的权限验证阶段，包括连接过程和语句执行过程在内。

	在 MySQL 8.0 版本里，如果你启用–skip-grant-tables 参数，MySQL 会默认把 --skip-networking 参数打开，表示这时候数据库只能被本地的客户端连接。

### 慢查询性能问题

1. 索引没有设计好； ^49df8f
	1. 重建索引:
		1. 在备库 B 上执行 set sql_log_bin=off，也就是不写 binlog，然后执行 alter table 语句加上索引；
		2. 执行主备切换；这时候主库是 B，备库是 A。
		3. 在 A 上执行 set sql_log_bin=off，然后执行 alter table 语句加上索引。
	2. 考虑累死 gh-ost 这样的方案. 紧急情况时, 第一个方案效率高.

2. SQL 语句没写好；
	1. 增加语法改写规则:

	```sql
	mysql> insert into query_rewrite.rewrite_rules(pattern, replacement, pattern_database) values ("select * from t where id + 1 = ?", "select * from t where id = ? - 1", "db1");

	call query_rewrite.flush_rewrite_rules();
	```

3. MySQL 选错了索引。
	1. 这时候，应急方案就是给这个语句加上 force index。同样地，使用查询重写功能，给原来的语句加上 force index，也可以解决这个问题。

前两种情况发现的比较多, 所以要按照规则做好模拟测试:

1. 上线前，在测试环境，把慢查询日志（slow log）打开，并且把 long_query_time 设置成 0，确保每个语句都会被记录入慢查询日志；
2. 在测试表里插入模拟线上的数据，做一遍回归测试；
3. 观察慢查询日志里每类语句的输出，特别留意 Rows_examined 字段是否与预期一致。（我们在前面文章中已经多次用到过 Rows_examined 方法了，相信你已经动手尝试过了。如果还有不明白的，欢迎给我留言，我们一起讨论）。

而如果是新项目的话，或者是修改了原有项目的 表结构设计，全量回归测试都是必要的。这时候，你需要工具帮你检查所有的 SQL 语句的返回结果。比如，可以使用开源工具 pt-query-digest(https://www.percona.com/doc/percona-toolkit/3.0/pt-query-digest.html)。

### QPS 突增

1. 如果白名单是一个一个加的, 那么确定业务方会下掉这个功能的情况下, 从数据库把白名单去掉.
2. 如果新功能是单独的数据库用户, 可以把这个用户去掉, 然后断开现有的连接. 这样这个新功能的 QPS 就会变为 0
3. 如果这个新功能和主题部署在一起, 可以使用查询重写, 重写为 `select "1"` 这个操作风险比较高
	1. 如果别的功能里面也用到了这个 SQL 语句模板，会有误伤；
	2. 很多业务并不是靠这一个语句就能完成逻辑的，所以如果单独把这一个语句以 select 1 的结果返回的话，可能会导致后面的业务逻辑一起失败。

方案 3 优先级最低. 方案都依赖规范的运维

### 小结

三种导致性能出现故障的原因: 分别是

1. 短连接
2. 长查询
3. QPS 突增
应对方法从应急, 权限管理, 语句改写等方面入手.

## MySQL' 饮鸩止渴 ' 提高性能的方法思考

你是否碰到过，在业务高峰期需要临时救火的场景？你又是怎么处理的呢？

- 如果是压力打挂的服务器, 重启没用: 重启之后，业务请求还会再发。而且由于是重启，buffer pool 被清空，可能会导致语句执行得更慢。

- 有时候一个表上会出现多个单字段索引（而且往往这是因为运维工程师对索引原理不够清晰做的设计），这样就可能出现优化器选择索引合并算法的现象。但实际上，索引合并算法的效率并不好。而通过**将其中的一个索引改成联合索引**的方法，是一个很好的应对方案。
