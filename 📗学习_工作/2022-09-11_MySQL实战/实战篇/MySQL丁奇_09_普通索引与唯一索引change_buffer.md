## 前言

## 普通索引和唯一索引和 change buffer

- 普通索引: 查到数据后, 为了防止重复数据, 继续往下查, 直到判断出不符合条件
- 唯一索引: 索引是唯一字段 (各不相同), 所以查到数据就会停止.

### 查询过程

![[附件/image/09_普通索引和唯一索引.jpg|500]]

```sql
select id from T where k=5
```

普通索引查找过程, 先通过按层搜索找到右下角的数据页 (3 - 5 - 6), 然后在页内部, 定位记录 (网友: 在数据页中，有一个 Page Directory 结构，内部维护多个槽，相当于是跳表中的多层索引，通过 Page Directory 实现在页内对行记录的 O(logn) 的查找效率, 这也解释了为什么会找到下一个去)

- 对于普通索引来说, 找到满足条件的第一个记录后, 还会查找下一个记录, 直到遇到第一个不满足条件的
- 对于唯一索引来说, 由于索引是唯一的, 查到第一个满足条件的记录就会停止检索.

其实这两个过程差距微乎其微: 因为 innoDB 内部是以数据页为单位来读写的, 相当于读一条记录要在内存中的整体页中读, 在 innoDB 中每个页的大小是 16KB

所以对于普通索引来说, 只不过在内存中多完成一次寻址, 差距很小; 除非正好是 k = 5 是最后一条记录, 那么就要多读一页到内存中.而一个数据页要放近千个 key, 所以这种情况概率不高.

### 更新 (包含插入) 过程和 change buffer

当需要更新一个数据时, 如果数据页已经在内存中就直接更新, 如果没有在内存中的话, InnoDB 会把这些更新操作记录在 change buffer 中, 这样就不需要再从磁盘读取这个数据页了. 当下次访问这个数据页时, 数据页被读入内存, 再应用 change buffer 的变更, 就可以了.

以上这个操作, 叫 **merge,** merge 会发生再 3 个时间点, 数据被读取时, 后台线程周期执行, 和数据库正常关闭;

所以 merge 是数据真正发生变更的时刻, 此时 change buffer 累计的越多, 性能收益就越大.

merge 的执行流程:

1. 从磁盘读入数据页到内存（老版本的数据页）；
2. 从 change buffer 里找出这个数据页的 change buffer 记录 (可能有多个），依次应用，得到新版数据页；
3. 写 redo log。这个 redo log 包含了数据的变更和 change buffer 的变更。
这时候这个数据页还没有落盘修改, 属于脏页, 之后还会刷入物理磁盘, 这就属于另一个过程了.flush

change buffer 不光会写在内存中, 也会持久化到磁盘里; 另外, 读数据页到内存是要占用 buffer pool 的, 这种方式也能提高 buffer pool 的利用率.

[[Redis蒋德钧_02_Redis中的数据类型和其数据结构#^772e3d|渐进式Rehash]] 里, 也应用了这种写时复制, 后台线程自动完成的思想

### change buffer 的使用场景

如果数据页已经在内存中, 那么不需要 change buffer 参与, 直接在内存页上修改就可以了;

如果是唯一索引, 不管是插入还是更改, 都要对数据进行唯一性判断, 所以不管怎样都要把数据页读到内存里的, 使用 change buffer 就显得有点不划算了; 而对于普通索引来说, 如果是一个插入操作, 完全可以不用读取内存页; 所以, 只有普通索引可以应用 change buffer;

change buffer 用的是 buffer pool 里的内存，因此不能无限增大。change buffer 的大小，可以通过参数 `innodb_change_buffer_max_size` 来动态设置。这个参数设置为 50 的时候，表示 change buffer 的大小最多只能占用 buffer pool 的 50%。

change buffer 减少将数据读入磁盘所涉及的随机 IO 的访问, 这是数据库最高成本的操作之一, 所以对性能提升很明显.

但是如果每次变更就要立即读, 那么 change buffer 难以有用武之地 (反正都是要读的, 不如先读出来); change buffer 的使用场景往往是账单类, 日志类.

### 索引选择和实践

建议使用普通索引. 查询性能大差不差, 更新性能却因为 change buffer 的存在相差甚多.对于数据量比较大的表性能优化尤其明显, 所以当面临一个大表 (历史数据较多), 机械硬盘时, 建议把它开大

如果每次更新完都伴随查询, 那么建议关闭 change buffer.

`innodb_change_buffering` 设置为 none

### change buffer 和 redo log

![[附件/image/09_普通索引和唯一索引change_buffer-1663265877875.jpeg]]

写

```sql
mysql> insert into t(id,k) values(id1,k1),(id2,k2);
```

过程

分析这条更新语句，你会发现它涉及了四个部分：内存、redo log（ib_log_fileX）、 数据表空间（t.ibd）、系统表空间（ibdata1）。

这条更新语句做了如下的操作（按照图中的数字顺序）：

1. Page 1 在内存中，直接更新内存；
2. Page 2 没有在内存中，就在内存的 change buffer 区域，记录下“我要往 Page 2 插入一行”这个信息
3. 将上述两个动作记入 redo log 中（图中 3 和 4）。

读过程 select * from t where k in (k1, k2)

![[附件/image/09_普通索引和唯一索引-1.jpg]]

1. 读 Page 1 的时候，直接从内存返回。
2. 要读 Page 2 的时候，需要把 Page 2 从磁盘读入内存中，然后应用 change buffer 里面的操作日志，生成一个正确的版本并返回结果。

可以看到，直到需要读 Page 2 的时候，这个数据页才会被读入内存。所以，如果要简单地对比这两个机制在提升更新性能上的收益的话，

redo log 主要节省的是 **随机写磁盘的 IO 消耗**（转成顺序写）

而 change buffer 主要节省的则是 **随机读磁盘的 IO 消耗**。

我的理解:

1. 区别 1: 流程侧重不同
	- change buffer
		- 更新的时候不需要读磁盘页, 直接写内存
		- 读的时候读磁盘页 + 执行落盘的修改
	- redo log
		- 写入的时候是一起顺序写 (减少随机写), 记录了 change buffer 的内容和与之对应的数据页
2. 区别 2: 目的不同, 前者是为了提高写的性能, 后者是为了保证 crash-safe 的性能

### 小结

1. 从普通索引和唯一索引的查询过程, 更新过程, 介绍了 change buffer 的使用方法以及对性能的提升
2. 对选择哪种索引有了判断 (普通优), 但如果写完立即要读, 就关闭 change buffer
3. 最后比较了 change buffer 和 redo log 的区别.

首先，业务正确性优先。这篇文章的前提是“业务代码已经保证不会写入重复数据”的情况下，讨论性能问题。如果业务不能保证，或者业务就是要求数据库来做约束，那么没得选，必须创建唯一索引。

这种情况下，本篇文章的意义在于，如果碰上了大量插入数据慢、内存命中率低的时候，可以给你多提供一个排查思路。

然后，在一些“归档库”的场景，你是可以考虑使用普通索引的。比如，线上数据只需要保留半年，然后历史数据保存在归档库。这时候，归档数据已经是确保没有唯一键冲突了。要提高归档效率，可以考虑把表里面的唯一索引改成普通索引。
