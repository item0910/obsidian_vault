## MySQL 如何保证高可用 - 主备切换

### 主备延迟

主执行完一个事务: T1

备接受完这个 binlog 的时间: T2

备执行完这个 binlog 的时间: T3

主备之间有一个时间差 T3 - T1

你可以在备库上执行 show slave status 命令，它的返回结果里面会显示 seconds_behind_master，用于表示当前备库延迟了多少秒。就是这个值, 单位是秒

如果主备库机器的系统时间设置不一致，会不会导致主备延迟的值不准？其实不会的。

因为，备库连接到主库的时候，会通过执行 SELECT UNIX_TIMESTAMP() 函数来获得当前主库的系统时间。如果这时候发现主库的系统时间与自己不一致，备库在执行 seconds_behind_master 计算的时候会自动扣掉这个差值。

### 主备延迟的来源

1. 主备性能差异: 现在都是对称部署
2. 备库压力大: 备库压力大于主库
	1. 一主多从。除了备库外，可以多接几个从库，让这些从库来分担读的压力。
	2. 通过 binlog 输出到外部系统，比如 Hadoop 这类系统，让外部系统提供统计类查询的能力。
3. 大事务
	1. 场景 1: 一次性 delete 太多数据: 控制多次删除
	2. 大表 DDL: 计划内的 DDL, 使用 gh-ost 方案
4. 备库的并行复制: [[MySQL丁奇_26_并行复制策略与MySQL版本]]

### 可靠性优先策略: 保证不出错

可靠优先的原则下的主备切换:

1. 判断备库 B 现在的 seconds_behind_master，如果小于某个值（比如 5 秒）继续下一步，否则持续重试这一步；
2. 把主库 A 改成只读状态，即把 readonly 设置为 true；
3. 判断备库 B 的 seconds_behind_master 的值，直到这个值变成 0 为止；
4. 把备库 B 改成可读写状态，也就是把 readonly 设置为 false；
5. 把业务请求切到备库 B。

这个切换流程，一般是由专门的 HA 系统来完成的，我们暂时称之为可靠性优先流程。

不可用时间: A 只读, 等待 seconds_behind_master = 0 这段时间, 所以也是为什么要等待这个数字足够小

### 可用性优先策略

把 4. 5 步骤调到最前面. 就不存在不可用的时间了, 但是会出现数据不一致

场景:

1. A 库收到插入 insert c = 4, 多了 (4,4)
2. B 库还没完成 A 的 log, 就执行了插入 5, 得到了 (4, 5)
3. A 传来 insert c = 4, 到 B 变为 (5, 4)
4. 而 A 收到 B 的 c = 5, 变为 (5, 5)
5. 这样, AB 就有两行数据不一致.

如果 binlog 是 row 格式的呢?

两边 的会报错 duplicate key error 并停止, 都不会被对方执行, 但是也会产生 1 行问题.

所以: 可靠性优先

一个场景:

- 有一个库的作用是记录操作日志。这时候，如果数据不一致可以通过 binlog 来修补，而这个短暂的不一致也不会引发业务问题。
- 同时，业务系统依赖于这个日志写入逻辑，如果这个库不可写，会导致线上的业务操作无法执行。
如何更改:
- 不要让业务依赖日志逻辑, 或者降级, 写到本地文件, 或者写到另一个临时库

如果主备延迟很高, 且主库突然不能使用, 我们怎么办

为了可靠性仍然要等到延迟时间 = 0 时, 才能进行操作.

所以要控制主备延迟时间, 不能太高

### 小结

1. 主备切换的操作逻辑, 延迟时间参数
2. 准备切换的两个原则: 可靠性, 可用性.
