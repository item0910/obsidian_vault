## 学前

索引就是为了提高查询效率, 就像给书加一个目录.

## 索引上 _ 索引数据结构

### 索引的常见模型

哈希表, 有序数组和搜索树
- 哈希表
	- 数组 + 链表
	- 适用于等值查询的场景, 不适合范围查询
- 有序数组
	- 查询效率很高, 无论是等值还是范围, 都是 logN 的复杂度 (二分查找)
	- 不适合需要频繁插入的情况, 适合保存静态数据
- 搜索二叉树
	- 为了 logN 的复杂度, 需要维护树的平衡,
	- 索引不只在内存中, 还要写在磁盘上, 导致二叉树读数据慢
	- 而且二叉树的叉不够多会导致速度比较慢
- N 叉树:
	- 树高低, 查询磁盘的次数少
- LSM 树, 跳表也有应用

MySQL 的索引是在存储引擎层中实现的, 所以没有统一的索引标准. 意味着不同的存储引擎的索引工作方式不同.

### InnoDB 的索引模型: B+ 树

我们有一个主键列为 ID 的表，表中有字段 k，并且在 k 上有索引。这个表的建表语句是：

```sql
mysql> create table T(
id int primary key, 
k int not null, 
name varchar(16),
index (k))engine=InnoDB;
```

![[附件/image/04_索引上_索引数据结构.jpg | 500]]
由图可知, 索引分为主键索引和非主键索引, 主键索引存储的是整行的数据, 也被称为聚簇索引
非主键索引存储的是主键的值, 也被称为二级索引.
- 二者查询的区别在于是否需要回表
如果语句是 select * from T where ID=500，即主键查询方式，则只需要搜索 ID 这棵 B+ 树；如果语句是 select * from T where k=5，即普通索引查询方式，则需要先搜索 k 索引树，得到 ID 的值为 500，再到 ID 索引树搜索一次。这个过程称为回表。
所以我们尽量使用主键查询

### 索引维护 - 主键选择

维护 B + 树的索引时, 如果插入新值, 自然会对树有调整, 当插入的数据页已经满了的时候, 就需要重新申请一个数据页挪动数据, 被称为 **页分裂** 对性能造成影响.
页分裂还影响数据页的利用率.
当然, 删除数据后, 页也会自己做合并.

#### 什么时候应该用自增主键?

自增主键是指自增列上定义的主键，在建表语句中一般是这么定义的：NOT NULL PRIMARY KEY AUTO_INCREMENT。

为什么自增主键比较适合
- 自增主键的插入数据模式，正符合了我们前面提到的递增插入的场景。每次插入一条新记录，都是追加操作，都不涉及到挪动其他记录，也不会触发叶子节点的分裂。
   而有业务逻辑的字段做主键，则往往不容易保证有序插入，这样写数据成本相对较高。
- 从存储空间来看, 主键长度越小, 普通索引的叶节点就越小, 那么普通索引也就越小.

什么时候适合用业务字段做主键呢?
1. 只有一个索引
2. 该索引必须是唯一索引
典型的 KV 场景.

## 学后思考

- 我给你留下一个问题吧。对于上面例子中的 InnoDB 表 T，如果你要重建索引 k，你的两个
SQL 语句可以这么写：

```sql
alter table T drop index k;  
alter table T add index(k);
```

如果你要重建主键索引，也可以这么写：

```sql
alter table T drop primary key;  
alter table T add primary key(id);
```

我的问题是，对于上面这两个重建索引的作法，说出你的理解。如果有不合适的，为什么，更好的方法是什么？
- 为什么要重建索引呢?
	- 因为数据在插入的过程中可能存储空间数据页有空洞, 创建数据按序插入, 索引页面利用率更高, 更省空间.
- 重建 K 的索引的过程是合理的, 重建主键索引不合理
	- 重建主键索引的话, 就会将整个表重建, 连着执行第一条就白执行了.
	- 代替 `alter table T engine=InnoDB`
